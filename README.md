# Combat Testbed

C# 콘솔 텍스트 RPG(**IF THE NIGHT COMES**)의 전투 코어를 **엔진에 의존하지 않는 순수 C# 로직**으로 다시 설계하고, **Unity 6(Universal 2D / URP)** 에 이식한 전투 시스템 테스트베드입니다.
로직과 화면을 분리해 엔진 없이도 **319개의 단위 테스트**로 검증하고, 자동 플레이 시뮬레이터로 밸런스를 수치로 확인합니다.

- 블로그(개발 일지): https://marshall-2.tistory.com/

## 왜 다시 만들었나 (v1 → v2 → v3)

| 버전 | 내용 | 한계 |
|---|---|---|
| v1 | 콘솔 TextRPG (블로그에 Day 1~10 개발 일지) | 로직과 출력이 섞여 있음 |
| v2 | 전투 메커니즘에 디자인 패턴 적용 (델리게이트 기반 Observer, 인터페이스 기반 Strategy) | `Game.cs` 934줄의 거대 클래스, 몬스터·보스 클래스 상속, 엔진 분리 불가, 테스트 없음 |
| **v3 (이 저장소)** | 순수 C# Core + MVP + Unity 이식, FSM, 데이터 주도 설계, 단위 테스트, 밸런스 시뮬레이터 | |

## 구조

```
CombatTestbed.Core          순수 C# (netstandard2.1, C# 9, noEngineReferences)
                            전투·스킬·상태이상·캠페인 규칙, 밸런스 시뮬레이터
CombatTestbed.Presentation  순수 C#. Presenter와 View 인터페이스 (MVP), 화면 흐름 FSM
CombatTestbed.Tests         NUnit 단위 테스트 (319개)
CombatTestbed.Unity         Unity 6 프로젝트. View(uGUI), ScriptableObject 데이터, 조립 지점
```

의존 방향은 `Unity → Presentation → Core`로 한 방향입니다. Core와 Presentation은 `UnityEngine`을 참조하지 않으므로 `dotnet test`만으로 검증됩니다.

### 주요 설계 결정

- **MVP**: Presenter는 View 인터페이스에만 의존합니다. 엔진을 바꾸면 View만 다시 만들면 됩니다.
- **FSM(상태 패턴)**: 범용 `StateMachine<TState>` 하나를 전투, 캠페인, UI 화면 흐름이 재사용합니다. 전이 중 재진입은 큐로 순서를 보장합니다.
- **상속 대신 데이터와 합성**: 몬스터와 보스는 클래스가 아니라 `ActorDefinition`(수치 + 행동 스킬 목록)입니다. 새 보스는 코드 없이 데이터로 추가합니다. 행동 선택은 `IActionSelector`로 추상화했습니다.
- **스킬 효과 조합**: 스킬은 직렬화 가능한 효과(`SkillEffectSpec`)의 조합이고, ScriptableObject에서 인스펙터로 수정할 수 있습니다.
- **난수 주입(`IRandomSource`)**: 테스트와 시뮬레이터가 시드를 고정해 결과를 재현합니다.
- **조립 지점 한 곳(`GameBootstrapper`)**: 구체 클래스 연결은 여기서만 하고, 전역 싱글턴은 쓰지 않습니다.
- **이벤트 규약**: 도메인 내부 제어 흐름은 명시적 호출, 외부 통보(UI/로그)는 과거형 이벤트(`DamageTaken`, `Healed`, `Died`)로 처리합니다.

## 실행 방법

**테스트**
```
dotnet test CombatTestbed.Tests
```

**Unity**
1. Unity 6(`ProjectSettings/ProjectVersion.txt` 참고)로 `CombatTestbed.Unity` 폴더를 엽니다.
2. `Assets/Scenes/SampleScene`을 열고 Play 합니다. (모바일 세로 3:4, 선택 버튼 5개)
3. 데이터는 `Assets/Data`의 ScriptableObject에 있습니다. 수치는 인스펙터에서 바꿉니다.
4. 메뉴 `Combat Testbed > Balance Simulator`에서 시뮬레이션을 실행합니다.

> `Combat Testbed > Generate Default Data`는 기본 데이터를 다시 생성하며 튜닝한 값을 덮어쓸 수 있으니 주의하세요.

## 밸런스 조정 내역

이전 버전(v2)에서 플레이로 빠르게 확인하려고 올려 둔 플레이어 공격력 300이 이식 후에도 남아 있어서, 거의 모든 몬스터가 한 방에 죽는 상태였습니다(베어펜리르만 예외). 처음에는 이식 과정에서 몬스터 수치가 잘못됐다고 의심했지만, 이전 버전과 하나씩 대조한 결과 **몬스터 수치는 모두 일치**했고 원인은 공격력이었습니다. 코드의 `DefaultActors`는 이전 버전 기준값으로 남겨 두고(테스트가 이 값을 사용), 조정값은 `ActorData` ScriptableObject에 적용했습니다.

| 대상 | 이전 (HP / 공격력) | 조정 (HP / 공격력) |
|---|---|---|
| 흡혈귀(플레이어) | 100 / 300 | 100 / 25 |
| 농부 | 20 / 2 | 40 / 4 |
| 사냥꾼 | 25 / 5 | 50 / 6 |
| 늑대 | 30 / 3 | 60 / 6 |
| 성직자 | 50 / 10 | 90 / 12 |
| 기사 | 80 / 17 | 90 / 12 |
| 늑대인간 | 60 / 15 | 70 / 10 |
| 반 헬싱 | 150 / 20 | 150 / 15 |
| 성기사, 라이칸, 베어펜리르 | 150·200·350 / 20·20·30 | 변경 없음 |

### 검증 방법
Core의 `CampaignSimulator`가 전략(`ISkillPolicy`)별로 캠페인을 자동 플레이합니다. 마스터 시드에서 판마다 시드를 만들어 결과를 재현할 수 있고, 에디터 창에서 단일 실행과 파라미터 스윕을 모두 돌릴 수 있습니다.

| 전략 | 클리어율 (1000판, seed 12345) |
|---|---|
| 항상 첫 스킬 (평타만 쓰는 캐주얼 플레이) | 33.4% |
| 눈앞의 최대 피해 | 33.4% |
| 무작위 스킬 | 0% (기준선으로만 사용) |

패배는 챕터 3 라이칸 구간(단계 3~5)에 몰립니다.

### 발견: 난이도 절벽
플레이어 공격력 스윕(항상 첫 스킬, 300판씩)에서 클리어율은 공격력 20이 0%, 25가 34.3%, 30 이상이 100%였습니다.
- 몬스터를 잡는 타수가 `ceil(HP / 공격력)`으로 계단식 변하고, 플레이어가 선공이라 타수가 줄면 반격도 같이 줄어듭니다.
- 피해를 덜 받은 만큼 보상이 쌓이고, 챕터 3에서 이 효과가 한 번 더 겹칩니다.

공격력 25를 기준값으로 정했습니다.

## 알려진 차이점 및 한계

- **붉은 달**: 이전 버전은 `currentHp *= 2`로 현재 HP를 두 배로 만들지만, 이식판은 최대 HP 증가분만큼 현재 HP를 올립니다.
- **최소 피해 1**: 방어력은 이전 버전에 없던 개념이라 모두 0입니다. 피해는 `max(1, 공격력 − 방어력)`입니다.
- **스킬 선택 깊이**: 시뮬레이터에서 "눈앞의 최대 피해"와 "항상 첫 스킬"의 결과가 같습니다. 평타가 즉시 피해 기준으로 항상 최선이라 현재 스킬 풀에는 의미 있는 선택 상황이 거의 없습니다. 개선하려면 상황 인식형 `ISkillPolicy`와 스킬 밸런스 조정이 필요합니다.
- **스킬 효과 확장**: 새로운 효과 종류를 추가하려면 효과 실행기를 수정해야 합니다. (개방-폐쇄 원칙을 완전히 지키지는 못합니다.)

## 개발 방식

이 프로젝트는 AI 도구와 함께 진행했습니다. 전체 기획과 구조는 Gemini에게 자문을 받았고, 구현·리팩토링·테스트 작성은 Claude와 페어 프로그래밍으로 진행했습니다. 자문과 제안은 대안을 비교해 직접 채택 여부를 결정했고, 단계마다 단위 테스트로 검증한 뒤 커밋했으며, 코드는 직접 읽고 해체해 이해하는 것을 원칙으로 삼았습니다.
